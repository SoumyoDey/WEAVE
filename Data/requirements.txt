# Install into a fresh venv or conda env:
#   pip install -r requirements.txt
#
# GEOS and PROJ: usually NOT needed on the host. This note used to say flatly
# that cartopy needs them installed, which sent a reader to apt for libraries
# pip was already providing.
#
# cartopy, shapely and pyproj all publish wheels for Linux (x86_64 and aarch64),
# macOS and Windows, and the wheels carry their own copies — shapely bundles
# libgeos/libgeos_c, pyproj bundles libproj, and cartopy itself links neither.
# The manylinux policy requires that: a wheel may not link GEOS or PROJ from the
# system. Measured on CI, which installs from these files and loads only
# `site-packages/shapely.libs/libgeos*.so` and
# `site-packages/pyproj.libs/libproj*.so` — see NEXT_STEPS.md §34 and the
# "Verify the compiled dependencies import" step in the test workflow.
#
# You need the system libraries only where pip has no wheel for you and falls
# back to the sdist — an unusual platform, a very new Python, or `--no-binary`.
# Then:
#   apt-get install libgeos-dev libproj-dev proj-data proj-bin
# or sidestep the build entirely with `conda install -c conda-forge cartopy`,
# which is what the development environment here does.

# Reads the source NetCDF files. `convert_aifs.py`, `convert_gefs.py` and
# `convert_ukmo.py` each `sys.exit` without it, and those three are what lets
# every forecast table be rebuilt from source — so this is a hard runtime
# dependency that was simply never declared. The cost of the omission was
# `test_convert_aifs.py`'s 14 file-reading tests skipping on every CI run
# (NEXT_STEPS.md §26); the cost of it in production would have been a converter
# that exits on a machine where `pip install -r requirements.txt` succeeded.
#
# Unlike cartopy above, this needs nothing from apt: the wheels bundle HDF5 and
# netcdf-c. 1.7.4 ships an abi3 wheel tagged manylinux_2_28, which ubuntu-24.04
# (glibc 2.39) satisfies; it pulls cftime and certifi and coexists with the
# numpy pin above.
netCDF4==1.7.4
